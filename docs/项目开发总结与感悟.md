# 网上书店项目开发总结与感悟

## 一、项目概述

本项目是一个基于微服务架构的网上书店系统，采用前后端分离设计，支持用户、商家、管理员三种角色。技术栈涵盖 Spring Cloud、Vue 3、MySQL、Redis、Spring AI 等，是一个功能完整、架构清晰的全栈电商项目。

---

## 二、项目收获

### 1. 微服务架构设计与实践

从单体架构重构为微服务架构是本项目最大的技术挑战，也是收获最多的地方：

- **服务拆分**：将系统拆分为 Gateway、User、Book、Order、Admin、AI 六个微服务，学会了按业务边界划分服务职责
- **API 网关**：使用 Spring Cloud Gateway 统一入口，实现路由转发、JWT 鉴权、跨域配置
- **服务间通信**：掌握 OpenFeign 声明式 HTTP 调用，实现服务间内部接口（InternalController）的安全通信
- **统一鉴权**：Gateway JwtGlobalFilter 统一处理认证，通过 X-User-Id Header 传递用户身份

### 2. 分布式问题解决

- **Redisson 分布式锁**：在库存扣减场景中使用 Redisson 实现分布式锁，保证并发安全
- **Redis 缓存策略**：合理设计缓存分层（bookCache 5分钟、categoryCache 30分钟），在读写操作中正确使用 `@Cacheable` 和 `@CacheEvict`
- **数据库分页**：将分页逻辑从内存分页迁移到 MyBatis-Plus `selectPage` 数据库分页，解决大数据量性能问题

### 3. 前端工程化

- **Vue 3 Composition API**：使用 `setup` + `ref`/`reactive` 替代 Options API，代码更简洁
- **Pinia 状态管理**：实现 Token、购物车、用户信息的全局状态管理
- **路由守卫**：通过 Vue Router 的 `beforeEach` 实现登录拦截和权限控制
- **组件化开发**：将 AI 聊天窗口封装为独立组件 `AiChat.vue`，悬浮嵌入用户侧布局

### 4. AI 能力集成

- **Spring AI 1.0.0**：集成 Spring AI 框架，通过 OpenAI 兼容接口接入小米 MiMo v2.5 大模型
- **智能导购**：AI 服务可查询图书数据，为用户提供个性化书籍推荐和问答服务
- **流式响应**：实现 Server-Sent Events 流式输出，提升聊天体验

### 5. 数据库设计

掌握了电商系统的核心数据建模：

| 实体 | 核心字段 | 说明 |
|------|---------|------|
| User/Shop/Admin | role, status | 三角色体系 |
| Book | price, stock, sales | 图书核心属性 |
| Order | status, shopId | 按商家分单 |
| OrderItem | orderId, bookId | 订单明细 |
| Review | rating, content | 评价体系 |
| Category | parentId | 树形分类 |
| Favorite | userId, bookId | 收藏功能 |
| Address | isDefault | 多地址管理 |

### 6. 开发工具与规范

- Knife4j API 文档自动生成，方便前后端联调
- Hutool 工具类简化常用操作（日期、加密、HTTP 等）
- 统一响应封装 `Result<T>` + 全局异常处理 `GlobalExceptionHandler`

## 三、存在的不足

### 1. 架构层面

| 问题 | 说明 |
|------|------|
| **缺少配置中心** | 各服务配置分散在本地 application.yml，无法集中管理，环境切换成本高 |
| **缺少链路追踪** | 微服务调用链路无监控，问题排查困难（未集成 SkyWalking/Sleuth） |
| **缺少熔断降级** | Sentinel 限流已引入但配置不完整，服务间调用缺乏完整的熔断降级机制 |

### 2. 安全层面

| 问题 | 说明 |
|------|------|
| **密码存储** | 需确认是否使用 BCrypt 等加密算法存储密码 |
| **接口限流** | Sentinel 限流规则未持久化，重启后丢失 |
| **XSS/SQL 注入** | 未实现全局输入过滤和参数校验 |
| **敏感信息** | Redis 密码、JWT Secret 等配置硬编码在配置文件中 |

### 3. 功能层面

| 问题 | 说明 |
|------|------|
| **支付功能** | 缺少真实的支付集成（微信/支付宝） |
| **库存超卖** | 虽然有分布式锁，但缺少数据库层面的乐观锁兜底 |
| **订单超时** | 缺少定时任务自动取消超时未支付订单 |
| **消息通知** | 缺少站内信、邮件、短信通知能力 |
| **搜索功能** | 图书搜索仅使用数据库 LIKE 查询，无 Elasticsearch 全文检索 |

### 4. 工程层面

| 问题 | 说明 |
|------|------|
| **测试覆盖** | 缺少单元测试和集成测试 |
| **CI/CD** | 无自动化构建和部署流程 |
| **日志规范** | 各服务日志格式不统一，缺少 ELK 日志聚合 |
| **接口版本** | API 无版本管理，后续迭代兼容性风险 |

## 四、改进方向

### 短期改进（可快速落地）

1. **完善 Sentinel 规则**：将限流规则持久化到 Nacos，实现动态配置
2. **添加数据库乐观锁**：给 `book` 表增加 `version` 字段，使用 `@Version` 注解防止超卖
3. **集成 Spring Security**：替代简单的 JWT 校验，提供更完善的安全防护
4. **补充单元测试**：为核心业务逻辑编写测试用例

### 中期改进（架构优化）

1. **引入 Elasticsearch**：实现图书全文检索、商品搜索、拼音搜索
2. **集成 RabbitMQ/Kafka**：实现异步消息处理（订单状态变更通知、库存同步）
3. **接入支付系统**：集成微信支付/支付宝，实现真实交易闭环
4. **定时任务框架**：引入 XXL-Job 实现订单超时取消、数据统计等定时任务
5. **分布式事务**：引入 Seata 解决跨服务数据一致性问题

### 长期改进（生产级部署）

1. **容器化部署**：使用 Docker + Kubernetes 实现服务编排和自动扩缩容
2. **CI/CD 流水线**：搭建 Jenkins/GitHub Actions 自动化构建、测试、部署
3. **监控告警**：集成 Prometheus + Grafana 实现服务监控和告警
4. **链路追踪**：集成 SkyWalking 或 Zipkin 实现分布式链路追踪
5. **日志中心**：搭建 ELK/EFK 日志聚合平台

## 五、技术选型反思

| 技术选择 | 当前方案 | 更优方案 | 理由 |
|---------|---------|---------|------|
| 注册中心 | 静态路由 | Nacos | 动态服务发现、配置管理 |
| 缓存 | Redis 单机 | Redis Cluster | 高可用、水平扩展 |
| 搜索 | MySQL LIKE | Elasticsearch | 全文检索、搜索性能 |
| 消息队列 | 无 | RabbitMQ | 异步解耦、削峰填谷 |
| 文件存储 | 本地磁盘 | MinIO/OSS | 分布式文件存储 |
| 容器化 | 无 | Docker + K8s | 标准化部署、弹性伸缩 |

## 六、个人感悟

### 1. 从单体到微服务的思维转变

微服务不是简单的"把代码拆开"。在重构过程中深刻体会到：
- 服务边界划分是最难的部分，划分不当会导致频繁的跨服务调用
- 分布式带来的问题（网络延迟、数据一致性、服务发现）远比单体复杂
- 微服务需要配套设施（注册中心、配置中心、链路追踪、日志聚合）才能发挥价值

### 2. 缓存设计的"双刃剑"效应

Redis 缓存极大提升了读性能，但也带来了缓存一致性、缓存穿透、缓存雪崩等问题。在项目中：
- `@CacheEvict` 必须在写操作时正确清除相关缓存
- 缓存 TTL 需要根据数据更新频率合理设置
- 分布式锁（Redisson）解决了并发场景下的数据安全问题

### 3. 前后端分离的协作模式

- 统一的接口规范（Result 封装）大幅降低沟通成本
- Knife4j 自动生成 API 文档，避免了手动维护接口文档
- 前端通过 Pinia + Axios 拦截器实现了 Token 自动注入和过期处理

### 4. AI 集成的探索

将 Spring AI 集成到电商场景是一次有价值的尝试：
- AI 导购能根据图书数据提供个性化推荐
- 流式响应提升了交互体验
- 但 AI 的幻觉问题仍需通过 RAG（检索增强生成）来缓解

### 5. 工程化意识的建立

项目开发过程中逐渐意识到：
- 编写测试用例不是"浪费时间"，而是后期重构的信心来源
- 日志规范化和链路追踪在排查问题时价值巨大
- CI/CD 流水线能有效避免"在我电脑上是好的"问题

---

## 七、总结

本项目从最初的单体 Spring Boot 应用，逐步演进为包含 6 个微服务的 Spring Cloud 架构，完整实现了用户管理、图书浏览、购物车、订单流程、商家后台、管理后台、AI 智能导购等功能。通过这次项目实践，深入理解了微服务架构的设计思想和落地挑战，积累了分布式系统开发的实战经验。

未来可以在服务治理、高可用、可观测性等方面持续优化，向生产级系统迈进。
